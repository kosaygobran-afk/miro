# POS design contract and complete acceptance matrix

Baseline 2026-10-06. All C01–C18 items below are implementation requirements, not claimed completions. The future agent maintains `IMPLEMENTATION_STATUS.md` with evidence and owner dependencies. Use the existing architecture described in `ARCHITECTURE.md`.

## Reference interpretation

User-provided references, stored only as documentation assets:

- `references/pos-desktop.png`: desktop category navigation/search, dense visual catalog, persistent cart/totals and payment commands.
- `references/pos-phone.webp`: portrait catalog with compact categories, readable product rows/quantity controls and bottom cart/checkout action.

Adapt those patterns to MIRO security products and existing management tokens. Do not reproduce food imagery, proprietary reference branding, physical device casing or unsupported hardware behavior. The references grant layout direction; they do not establish rights to publish their images as marketing assets.

Desktop: a stable cart/customer/payment region alongside a flexible searchable product grid, clear selected categories, SKU/barcode entry, stock and variant information, visible totals and sticky primary checkout action. At narrower container widths reflow rather than clipping. Phone: touch-friendly category control/list or rail, compact catalog rows/cards, deliberate cart drawer/screen and bottom cart summary/payment action. Do not force a scaled-down desktop grid into 320px. Avoid nested scroll traps and keep focused fields visible above the keyboard.

Keep Hebrew RTL/English LTR, locale-correct ILS display with cents, dates in business time, logical CSS and LTR numeric entry where helpful. Labels/status/error/help all localized. Preserve management dark and the existing medium/light themes; no public neon theme injection. Test reduced motion, zoom, text wrapping, long product names, pending/error/empty states and role-restricted controls.

## Fullscreen is a device/view mode

Existing floating-window maximize uses an inset desktop rectangle; it does not fulfill the request. Add separate states for normal floating bounds, viewport edge-to-edge POS and native fullscreen availability/active state. Save prior bounds/draft and restore them after exit, refresh recovery, rotation and provider-return navigation.

On a deliberate user click/tap, request supported native fullscreen and listen to `fullscreenchange`/`fullscreenerror`. Preserve a visible exit control and honest fallback label. Unsupported/denied native fullscreen must still use a borderless `100dvh` viewport mode with safe-area insets and keyboard/visualViewport handling. Do not claim unsupported browsers can hide all browser/system chrome. Feature-detect and test real Android/iPhone; WebKit emulation alone is not proof.

**Portal constraint:** dialogs currently use `mgmt-overlay-portal-host` under the shared overlay stack. Fullscreening only the tool element can hide portals outside that subtree. Prefer fullscreening `document.documentElement` while making the selected POS edge-to-edge and coordinating background/scroll/focus, or explicitly introduce a scoped portal host inside the fullscreen root. Verify review, payment, help, drawer and nested confirmations all remain visible/clickable and in the same overlay stack. Do not introduce a second independent modal context. Native fullscreen is presentation, not authorization or inertness; background keyboard interaction must still be managed.

Escape dismisses the top overlay first; browser fullscreen exit is observed, and window minimize/close must not happen accidentally. Existing floating-window document Escape listeners deserve a focused multi-window regression: only the active intended window responds after overlays have settled. Opening the calculator/help must not minimize every restored tool. Return focus to the correct trigger on overlay/fullscreen exit, remove resize handles in edge-to-edge mode and prevent stale body scroll locks.

Payment redirects may exit fullscreen or leave the page; intent/draft restoration and payment-status recovery must work independently. Do not demand fullscreen as a condition for payment. Snapshot only the permitted local draft data; never card details, signing/allocation secrets or provider tokens in local/session storage. Assess existing customer-data draft retention and clear it on successful completion, logout/user change and approved expiry; minimize unnecessary PII persistence.

## Required cashier capabilities

| Area                  | Required behavior                                                                                                                                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Product selection     | Active sellable variants, categories, name/SKU/barcode search, exact scan Enter-add, optional approved photos, stock/price visibility and duplicate-line merge                                                                                   |
| Cart                  | Quantity/variant change, remove/clear with deliberate recovery, unit/line/order discounts under explicit permission, gross/net/VAT/rounding and balance; canonical repricing before commit                                                       |
| Customers             | Linked or permitted guest buyer, editable billing details until issue, field validation and privacy minimization; email must not be forced merely because the old sale schema requires it without reviewing policy                               |
| Drafts                | Park/resume/list named drafts, persist after accidental close/reload, explicit discard, actor isolation, expiry/revalidation and multi-tab conflict handling; draft is not reserved stock unless server hold exists                              |
| Tenders               | Cash/change, verified hosted card, bit redirect/QR where enabled, external terminal/bank/check manual record with evidence/status, split tender and remaining balance; only supported installment counts                                         |
| Payment lifecycle     | Review accepted totals, pending/authorized/paid/failed/cancelled/unknown, retry after query, partial-payment recovery, double-submit protection and document-pending state                                                                       |
| Completion            | Order reference, readable receipt/document status, download/print/reprint, delivery with consent/approved channel, start-next-sale without losing pending previous operation                                                                     |
| History               | Search by order/document/customer/date/amount, tender/provider status, source badge, document chain, refunds and audited void/return handling                                                                                                    |
| Returns/refunds       | Explicit permission and reason, partial/full bounded amount, original tender/transaction, credit/correction document policy, independent physical stock-return decision                                                                          |
| Shift/cash            | Cash opening/closing/count/expected-vs-counted variance and staff audit if cash is used; no claim of bank reconciliation from counted cash                                                                                                       |
| Hardware              | Keyboard-wedge barcode scanner and browser print baseline, A4/80mm preview, optional camera scanning with permission if implemented; certified terminal/printer/cash drawer integrations gated by actual configured capabilities                 |
| Services/manual lines | Existing POS supports catalog UUID variants only. If added, create a real typed authorized non-stock sale-line contract and tax/pricing policy; never pseudo-UUID or fake inventory rows. Otherwise retain clear separate quote/service workflow |
| Operations            | Connectivity/session expiry, stale quote, low stock, price change, pending holds, payment/document exceptions, audit trail and operator reconciliation queue                                                                                     |

Basic browser printing is not a promise of silent thermal printing or automatic drawer opening. Offline mode may preserve/review a draft; never queue autonomous charges or issue official offline documents without an explicitly approved sequencing/security design. Discounts, returns and cash corrections need permissions/audit rather than merely hidden buttons.

## Contextual help

Provide a `?` control or contextual description for non-obvious decisions, using the existing tooltip/popover system. Hover and keyboard focus reveal short text; phone tap opens a dismissible help popover. Associate content using accessible descriptions, keep focus order predictable and support Escape. Tooltips must remain visible while pointer moves over them and avoid covering the action being explained. Standard Add/Remove/Close buttons need a clear label, not a redundant paragraph.

Explain at least: recorded external tender vs verified collection; authorization vs charge vs settlement; split balance/compensation; invoice vs receipt vs credit note; VAT inclusion and rounding; stock hold/expiry; refund vs physical return; no-obligo availability; installment vs recurring cancellation; cash variance; document pending/signature/allocation failure; report scopes. Keep help about business actions, not database/provider implementation internals. Confirm hover/focus/tap behavior in fullscreen and at 320px.

## Failure and race tests that cannot be omitted

| Boundary        | Scenarios                                                                                                                                                  | Expected invariant                                                           |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Price/money     | Manipulated prices/tax/discount/source; fractions, unsafe integers, huge quantities; tax change while cart open                                            | Server authority and bounded exact totals; re-review stale quote             |
| Stock           | Two buyers for last unit; duplicate item ordering; hold expiry racing callback; other POS sale while hold active                                           | No oversell/negative stock, deadlocks controlled, one stock consume          |
| Attempts        | Double-click/two tabs; same key changed payload; provider timeout after accepting request; reload before UID save                                          | Same operation or conflict, reconciliation before charging again             |
| Webhooks        | Invalid signature, wrong bytes/merchant/environment/currency/amount, replay, refund event as charge, out-of-order callback                                 | No unauthorized/duplicate financial transition                               |
| Lifecycle       | Browser success before callback, no redirect, cancellation without provider cancel, late capture after expiry, SQL down after provider capture             | Stored pending/unknown truth, durable retry/exception, approved compensation |
| Split/refund    | Successful leg + failed leg, double refund, concurrent refunds, amount above remaining balance, pending refund timeout                                     | No overcollection/overrefund; partial state preserved                        |
| Documents       | Concurrent issuance, reserved-number failure, settings changed mid-issue, double job, signer/allocation unknown/reject, crash after signing before publish | Same snapshot/number/artifact, no duplicate issue, visible exception         |
| Tax             | Entity exempt vs registered, allocation strict >5000 current/date-specific >10000, VAT-inclusive discount rounding, partial receipt/refund                 | Correct approved type/threshold/policy; no guessed allocation                |
| Identity/access | Customer A reads B's order/PDF, guest enumerates UUIDs, worker writes, admin config write, generic settings overwrite, auth delete                         | Least privilege, protected config, fiscal records preserved                  |
| Upload/export   | Fake MIME, malicious SVG/HTML, oversize/path traversal, unauthenticated URL, formula cells, long Hebrew filenames                                          | Private safe objects and safe readable exports                               |
| Recovery        | Outbox lease expiry/two workers, retry cap, reconciliation alert, object missing on restore, credential/certificate expiry                                 | One effect, bounded exception escalation and verified recovery               |
| Dates/reports   | Israel DST crossings, UTC analytics labels, filters vs exported summary, fees/COGS/expenses double-count                                                   | Consistent scope and honest totals                                           |

Provider fixture tests are meaningful for code correctness; only real signed sandbox exchanges prove that the adapter matches the provider. Mocked browser saves prove UI behavior, not persistence. Isolated SQL suites prove stored invariants, not deployment. Record these distinctions in evidence.

## Verification protocol

For each milestone, run focused tests plus required checks; fix failures by root cause and rerun affected regressions. Final pass: lint/typecheck/build/format, all unit/SQL suites, end-to-end browser/API/data effects, Chromium/Firefox/WebKit, Hebrew/English, three themes, 320/390/1440px, reduced motion, zoom and keyboard. Scan axe in settled and overlay-open states and record console/runtime errors. Inspect A4/80mm PDF/print renderings with long multi-page Hebrew/English data and verify signatures/allocation through their approved tools.

Add proposed suites such as `tests/commerce-checkout.spec.ts`, `tests/pos-commerce.spec.ts`, `tests/unit/commerce-*.test.mjs`, `supabase/tests/commerce_*.sql`, and a sanitized `scripts/verify-commerce.mjs`. Test state and observed side effects, not only strings in source. New fixture scripts must clean disposable actors/business rows and avoid using production money/document sequences. Do not expose service keys in browser setup logs.

An independent QA child audits all C01–C18 evidence and attempts adversarial cases. The primary reviews actual diffs/queries, performs integration and updates status after every meaningful change. Manual reviewers cover screen readers, real devices/fullscreen/printing and accountant-reviewed output. Complete a runbook with invalid credential recovery, paused gateway, reconciliation backlog, document issuance outage, allocation outage, backup restore and rollback without historical deletion.

The previous runtime-repair baseline passed 78 unit tests, 41 migrations/13 SQL suites and English/Hebrew × desktop/phone overlay browser checks; that is historical evidence, not proof for new commerce code. Rebaseline after changes and increase coverage according to new invariants rather than copying these counts as a target.
