## Why the layout changed

The owner reported that the catalog's list view stretched one product across the full width and left a large action column and unused space. The new Version 2 list fits up to two products on each row when the catalog is wide enough. A card uses a compact image and identifier area beside the category, title, model and price; its existing four actions span a joined footer. Smaller available widths fall back to one card per row, and narrow cards stack the same content. The grid/list selector changes only the presentation: products, sorting, filtering, prices, availability and action behavior use the existing data and components.

The other pending refinements expose the actual root/subcategory path on product surfaces, make the joined action hover fill reach its cell edges, and reserve space for native scrollbars and focus outlines across affected public and management scroll regions.

## Layout and behavior contracts

- `src/styles/public-refinement.css` owns the list layout and remains the last public style import. The list grid uses available **catalog** width, a 28rem minimum per column and the existing 0.9rem gap, capped at two columns. Keep the gap in the column calculation aligned with the actual grid gap. An existing card inline-size container switches its preview source to image/summary columns at 27rem; the list image stage is 9.5rem high. At narrower card widths the content stacks and stock/SKU keep their full-width halves. These are container-dependent, not fixed viewport-only decisions.
- The image, badge rail, stock/SKU band, category/title/model summary and price panel remain in the preview source. The four 48px cart, details, save and preview controls stay independent in a separate full-width footer. Preserve keyboard focus, hint portals and Escape, SKU copy feedback, touch/long-press boundaries, genuine unavailable-cart reasons and product-image containment. Allow long category, SKU and price content to grow or use the existing accessible overflow behavior; never force a fixed height that clips content. The list geometry is Version 2 only; grid, moving/related rails and Version 1 keep their existing layout.
- Stock remains physically left and SKU physically right in both languages, with each half reading in its locale and the actual SKU isolated left-to-right. Price remains physically left with localized context to the right. Do not create discounts, availability, descriptions or specifications to fill space. Retain the real image pixels, semantic status colors, existing theme tokens, reduced-motion behavior and all three public themes.
- Joined footer cells retain square interior corners and only the card's two outer bottom corners. Their gold hover/focus paint reaches the seams. The important radius declarations in the final public layer intentionally override older standalone icon radii; changing only computed values is insufficient evidence, so keep the actual screenshot-pixel regression.
- Native scrollbars may overlay their track and nearby focus rings. Preserve the added clearance, existing scroll behavior and keyboard/touch access; do not replace native scrolling with clipped content. Root/category chips and commerce navigation use a 1rem bottom inset and normal scrollbar width. Gallery, preview, POS, chart and table clearances have their own smaller or responsive values.

## Category paths and routes

`src/features/catalog/product-category-path.tsx` renders the root label (falling back to the category key), then the optional assigned child, with each value isolated by `bdi`. Product cards, quick previews and detail headings use this shared renderer in both appearance versions. Long card paths wrap; root-only products have no separator or invented child. The product-detail breadcrumb links a real child to the resolved root route using the literal `subcategory` slug encoded as a query value.

Keep the root/child projections, authorization, two-level database guards and root alias handling in `docs/CATALOG_CATEGORIES.md`. Do not normalize a child slug as a root alias or reclassify owner products for testing. This change reads existing projected labels and changes no catalog rows.

## Repeatable verification

Use an existing local server only if it is already running the current source; otherwise start an isolated server without disturbing an owner's process. The browser suites block analytics; they do not edit owner catalog data. List tests need at least three visible products and use browser-only synthetic long values and mocked clipboard writes. The category-path browser check skips its child-specific flow if no visible product has an assigned subcategory. The scrollbar suite uses synthetic DOM and CSS rather than live business records.

```sh
npm run lint
npm run typecheck
node --test --test-concurrency=2 tests/unit/*.test.mjs
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3000 PLAYWRIGHT_REUSE=1 npx playwright test tests/product-list-layout.spec.ts tests/product-category-path.spec.ts tests/scrollbar-clearance.spec.ts tests/catalog-reference.spec.ts --grep 'list view fits|category hierarchy appears|scrolling controls keep|compact preview thumbnails|reference cards and view controls|joined card actions fill' --workers=1
PLAYWRIGHT_BASE_URL=http://127.0.0.1:3000 PLAYWRIGHT_REUSE=1 npx playwright test --config=playwright.cross-browser.config.ts tests/product-list-layout.spec.ts --project=firefox --workers=1
```

The list regression exercises both languages, 320–1920px and breakpoints, card and action containment, long values, copying, preview keyboard behavior and switching views. The focused Chromium checks also inspect joined-cell hover pixels, child navigation and scrollbar clearance. A prior scoped accessibility pass checked both languages at 320/1077px in Dark, Medium and Light with glass enabled; it does not replace manual review. For release builds, use an isolated ignored temporary app and a relative build directory, exclude all repository environment files, and leave the owner's `.next` and development server alone.

A separate ignored checkout was installed with the declared npm 11.18.0 and the lockfile, then built and checked with Next.js 16.4.3.
