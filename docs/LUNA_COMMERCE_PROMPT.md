# הוראות ביצוע ל־Codex עם Luna — MIRO commerce

תאריך בסיס: 2026-10-06. זהו פרומפט לביצוע עתידי, לא אישור שהמערכות כבר מומשו.

## המשימה והחלטות הבעלים

פעל כ־Codex עם המודל Luna שבחר הבעלים. השלם את הרחבת MIRO למערכת ישראלית הכוללת סליקת אשראי אמיתית, bit, עמוד תשלום באתר, ניהול הוצאות, דוחות, **מנוע חשבוניות עצמאי באתר**, הגדרות פרטי עסק וקופה למחשב ולטלפון. לבעלים אין כרגע חשבון סליקה או חשבוניות. אין להחליף את דרישת החשבוניות העצמאיות במנוי חובה אצל ספק חשבוניות.

הכן חיבורים מסודרים לספק סליקה ולרשות המסים, כדי שהבעלים יוכל לחבר חשבונות והרשאות בהמשך. ממש את מה שאפשר לבדוק ללא חשבונות: מודלים, הרשאות, מסכים, מתאמים, בדיקות חוזה, סימולטור מקומי מבודד, מצבי כשל ותיעוד הפעלה. ציין בנפרד בדיקות sandbox שתלויות בחשבון ובדיקות ייצור שלא בוצעו. אין להציג סימולציה כתשלום אמיתי או PDF לדוגמה כחשבונית רשמית.

כלול "חיוב ללא אובליגו" כדרישה מפורשת. משמעותה אינה מאושרת: היא עשויה להתייחס למסגרת הכרטיס של הלקוח או לתנאי האשראי של העסק. הכן יכולת ותהליך מתאימים, אך אל תבטיח אותה ואל תפעיל אותה עד הגדרה ואישור כתוב מהספק והבעלים. תשלומים רגילים, הרשאה J5 וחיוב חוזר אינם הוכחה לעמידה בדרישה זו.

מראה הקופה נשען על `docs/commerce/references/pos-desktop.png` ו־`pos-phone.webp`: צפיפות ומבנה של קופה, מותאמים למוצרי האבטחה ולעיצוב MIRO. נדרשים קטלוג, עגלה, לקוח, תשלום, סקירה, היסטוריה, מסמכים, החזרים ועזרה לפעולות לא ברורות. כפתור מסך מלא ימלא את שטח התצוגה הזמין של המכשיר ויבקש fullscreen מקורי כשנתמך; הרחבת חלון עם שוליים אינה מספקת. בטלפון עזרה חייבת לפעול גם בנגיעה ובמקלדת, לא רק hover.

## קריאה ראשונה, בלי לבזבז הקשר

1. קרא `AGENTS.md`, את הרשומה החדשה ביותר ב־`docs/PROJECT_STATUS.md`, ואת הפרומפט הזה.
2. קרא `docs/commerce/ARCHITECTURE.md` ואת טבלת הדרישות ב־`docs/commerce/POS_AND_ACCEPTANCE.md`. הן מפת הקוד והיקף העבודה. קרא `PROVIDERS_AND_ISRAEL.md` לפני כתיבת חיבור חיצוני או מסמך רשמי.
3. בדוק `git status --short`, HEAD והעדכונים המקומיים. תיעוד המחקר אינו תחליף לבדיקה עדכנית. אל תעשה reset, החלפת ענף או pull לתוך עבודה מקומית מלוכלכת. בדוק remote לקריאה בלבד; שלב שינוי מרוחק רק בצורה שמגינה על העבודה הקיימת.
4. לפני קוד Next.js קרא את המדריך הרלוונטי מתוך `node_modules/next/dist/docs/`; מותקנת גרסה 16.3.8 בבסיס המחקר. אל תניח ש־API מגרסה קודמת מתאים.
5. קרא קבצים לפי בעלות השלב, לא את כל ההיסטוריה. היעזר ב־`rg`. מדריכי עיצוב/אנימציה והרשאות קיימים מחייבים רק כאשר נוגעים באותו תחום.

המצב הקיים כבר כולל קופה ודוחות. תקן והרחב אותם; אל תיצור אפליקציה מקבילה. ההוראות הישנות להגבלת האתר ל־enquiry מתארות את הבסיס: הבעלים אישר כעת הרחבת commerce, אך התנהגות enquiry נשמרת למוצרים שלא אושרו למכירה ולכל עוד תשלום אמיתי כבוי.

## סדר ביצוע ותנאי יציאה מכל שלב

### 0 — בסיס ותוכנית מחייבת

תעד dirty state וקבע baseline. הרץ lint, typecheck, unit tests, database verifier ו־build. בדיקות SQL כותבות ירוצו במסד מקומי מבודד; חוסר בחשבון ספק אינו מונע אותן. דווח על בדיקות חיצוניות שלא ניתן להריץ, בלי להציג fixture כבדיקת ספק אמיתית. אם בדיקה נכשלת, הפרד כשל בסיס מכשל חדש לפי ראיות; אל תעקוף הרשאות או תשנה expected כדי להסתיר באג. בדוק את תיקון overlay/calculator שכבר קיים. אמת את מצב ה־migrations המקומי והמקושר בקריאה בלבד, ודווח מה באמת הוחל; אל תניח שרשימת החסמים ההיסטורית עדיין עדכנית ואל תחיל migration כדי לבדוק זאת. שמור ראיות חדשות בתיקייה מתוארכת, בלי לדרוס evidence היסטורי.

צור `docs/commerce/IMPLEMENTATION_STATUS.md` עם שורה לכל מזהה C01–C18: planned / in-progress / implemented / locally-verified / sandbox-verified / live-verified / owner-blocked. קבע חוזי כסף, מצבים, endpoints, בעלות SQL וסוכנים. אין לסמן דרישה complete בגלל כפתור או stub. זוהי תוכנית ביצוע, לא רשימת פיצ'רים דמיונית.

### 1 — יסודות עסקיים והרשאות

ממש כסף באגורות, אימות מחירים/מלאי/מע"מ בשרת, settings עסקיים versioned, permissions מפורשים, reservations, payment attempts/events, outbox ו־state transitions. שמור תאימות להזמנות הקיימות. SQL tests חייבים להוכיח atomicity, RLS, revision conflict, idempotency ו־concurrency. סודות אינם שורות settings. אל תקשר שימור מסמך רשמי למחיקת auth user.

### 2 — סליקה וחיבורים

ממש מתאם PayPlus ראשוני לפי התיעוד הרשמי העדכני, simulator נפרד ו־contract tests. PayPlus הוא ברירת מחדל מוצעת למחקר sandbox, לא בחירה מסחרית סופית. Checkout/קופה ישתמשו באותו מנוע תשלום. ביט, כרטיס, תשלומים, terminal וחיוב חוזר מופעלים רק לפי capabilities מאושרים. בדוק חתימות וסטטוס בשרת; return URL אינו אישור תשלום. בלי חשבון: השלמת קוד/fixtures והוראות חיבור, עם banner sandbox ו־live כבוי. אל תשאיר "success" קבוע כאשר חסר credential.

### 3 — חשבוניות עצמאיות והגדרות

ממש מנוע פנימי, פרטי עסק editable ל־CEO, טיוטה/preview, מספור SQL, מסמכי מס/קבלות/זיכויים לפי סוג העסק, snapshot בלתי משתנה, A4/80mm, אחסון פרטי והרשאות הורדה. חבר interfaces לחתימה אלקטרונית ולהקצאה; שמור מצבי pending/failed/unknown ונסיונות בירור. לא מחייבים ספק SaaS לחשבוניות. מצב רשמי כבוי עד בדיקת רו"ח/תחולה, פרטי העסק, חתימה/הקצאה נדרשות ותהליך שימור/יצוא. מקורות ומגבלות ב־`PROVIDERS_AND_ISRAEL.md`.

### 4 — הוצאות ודוחות

ממש הוצאה, ספק, שורות, מע"מ/פטור, אסמכתא פרטית, תשלום, סטטוס אישור, תיקון/ביטול audited, חיפוש/מסננים/יצוא. כפל מסמך ספק מסומן לבדיקה. אל תניח שכל מע"מ הוצאה מותר בניכוי. הפרד מכירות, גבייה, סליקה לבנק, החזרים, עלות מכר והוצאות; הצג scope ואזור זמן. רווח נקי/דוח מס אינם טענה מותרת בלי מודל חשבונאי ואישור.

### 5 — POS ואתר, במחשב ובטלפון

יישם את חוזה `POS_AND_ACCEPTANCE.md`, כולל native fullscreen/fallback, portal בתוך העץ הנראה, draft restoration, תשלום אסינכרוני, bit redirect/QR, נגישות עזרה ו־320px. שמור שלוש ערכות נושא, שתי שפות ותנועות מופחתות. פצל את `pos-window.tsx` הגדול לרכיבים/תחומי לוגיקה בהדרגה סביב הגבולות החדשים; אל תשכתב הכול בלי ראיות.

### 6 — אינטגרציה, כשל, תיקון ובדיקה חוזרת

בכל שלב: השווה ל־acceptance → הרץ בדיקות בתחום ששונה → אתר סיבת שורש → הצע פתרון → תקן → הרץ את הבדיקה שנכשלה ואת הרגרסיות הקשורות. אם אותו כשל חוזר, שנה את ההשערה לפי הראיות; אל תחזור עיוור על אותו patch. אחרי הצלחת הבדיקות המתאימות המשך לשלב הבא. בסוף הרץ את כל הבדיקות המחייבות ומטריצת הדפדפנים; אין צורך להרחיב ללא גבול בדיקות שכבר עברו ולא הושפעו.

אין auto-retry של חיוב/החזר/הפקה במצב תוצאה לא ידועה. תחילה query/reconcile לפי מזהה יציב. גם חתימה והקצאה חיצוניות כפופות לכך: שמור operation/effect ID ומספר מסמך, וברר את הפעולה המקורית לפני המשך. נסה מחדש רק פעולה שהוכחה כאידמפוטנטית או שלא הושלמה; אין להקצות מספר חדש או להפיק מסמך שני כדי לפתור timeout. retries של outbox יהיו bounded, leased, idempotent ועם quarantine/התראה למפעיל. ספק חיצוני אינו משתתף בטרנזקציית PostgreSQL; בדוק compensation ותוצאה מאוחרת.

עדכן `PROJECT_STATUS.md` אחרי כל שינוי משמעותי עם מה/למה/פקודות ותוצאות/בעלים וחסמים משפטיים, פרטיות ונגישות שנוספו. עדכן את סטטוס C01–C18 עם קישור לקוד, בדיקה וראיה. קבל מסוכן QA סקירה עצמאית לפני סיום. אם רעיון טוב יותר עולה, השווה אותו מבחינת נכונות כספית, שימור, UX, אבטחה, עלות ומורכבות; תעד החלטה קצרה ב־ADR, שנה חוזים ובדיקות יחד ואמת מחדש. אין צורך באישור לכל החלטה הפיכה במסגרת הדרישות.

## פקודות בסיס וסגירה

```sh
npm run lint
npm run typecheck
node --test tests/unit/*.test.mjs
python3 scripts/verify-database.py
npm run build
npm run format:check
git diff --check
```

לבדיקות browser הפעל build production על פורט פנוי ותעד אותו. תיקון כלי הניהול ניתן לבדיקה עם:

```sh
ADMIN_BASE_URL=http://127.0.0.1:3121 node scripts/verify-management-tools.mjs
```

הפורט הוא דוגמה; ודא שזה השרת שלך. הרחב או הוסף בדיקות commerce תחת scripts/tests. `verify-business-console.mjs` ו־`verify-reporting-workspaces.mjs` משתמשים גם בשחקני auth חד־פעמיים; קרא אותם לפני הפעלה, נקה שחקנים ונתונים והשתמש ב־`CONSOLE_OUTPUT_DIR`/`REPORTING_OUTPUT_DIR` חדש. בדיקות כתיבה כספיות ירוצו במסד מבודד ובספק sandbox. בדיקות cross-engine משתמשות ב־`playwright.cross-browser.config.ts`; קרא את תנאי opt-in וה־base URL שלה לפני ההרצה.
